## Поток данных (цикл кадра)

```
Событие → IcedEditor::update()
  ├─ клавиатура → api::{text,cursor} → dirty = true
  └─ мышь → buffer.hit() → request_redraw()

Кадр → IcedEditor::draw()
  ├─ dirty? → zoll::parse_document()
  │         → layout::compute_line_runs() для каждой строки
  │         → render::shape_document() (cosmic-text Buffer)
  │         → только видимые строки (viewport optimization)
  └─ render: fill_text() для фона, глифов, курсора
```

## Зависимости крейтов

```
main.rs
  └── gui
        ├── api
        │     └── editor
        │           ├── zoll
        │           ├── layout, render, markup, cache
        │           ├── cursor, font, theme, utils, state
        │           └── rhai
        └── editor (через api)
              └── zoll
```

Все зависимости направлены **вниз**: gui → api → editor → zoll. Циклических зависимостей нет.

## Конкурентность

- **Однопоточный** — Iced работает в главном потоке.
- **Синглтоны шрифтов** — `FontSystem` и `SwashCache` обёрнуты в `OnceLock<Mutex<...>>` для безопасного доступа.
- **Нет async** — асинхронных операций нет. Сохранение файла синхронное.

## Система ручек (handles) и конвейер

### Идея

Ручка — это действие, не данные. Вызов ручки = запрос на изменение.
Ручка не возвращает состояние, она только принимает вход и ничего не отдаёт.

```
ручка: fn(вход) → void
```

Никто ничего не «читает», никто ничего не «синхронизирует».  
Плагин не спрашивает «какой сейчас цвет курсора?», он говорит «поставь курсору красный».

### Три слоя ручек

```
┌────────────────────────────────────────────┐
│  РЕЕСТР РУЧЕК (ядро)                      │
│  set_tab_width(4)                         │
│  set_cursor_color("#f00")                 │
│  toggle_preview()                         │
│  insert_text("hello")                     │
│  ...                                      │
└──────────┬──────────────┬─────────────────┘
           │              │

┌──────────────────┐  ┌──────────────────────┐

│  (статика)       │  │  (динамика)          │

│ theme = "dark" ──┼──┤ set_theme("dark")    │
│                  │  │                      │

                        │   копии реестра)     │

```

### RON-слой

Статические данные, которые читаются один раз при старте.
Каждое значение превращается в вызов ручки:

```ron
Config(
    tab_width: 4,
    font_size: 14,
    theme: "dark",
)
```
→ `set_tab_width(4)`, `set_font_size(14)`, `set_theme("dark")`.

В рантайме RON не нужен — он уже разложен по ручкам.

### Rhai-слой

Динамика: хоткеи, макросы, кастомные команды.
Дёргает те же ручки, что и RON, но в рантайме, по событиям.

```rhai
on_key("Escape", || { set_mode("Preview"); });
on_key("Ctrl-P", || { toggle_preview(); });
```

### Плагины

Плагин получает изолированную копию реестра ручек.
Он не может читать/писать состояние напрямую — только вызывать ручки.
Ядро решает, применять результат плагина или нет.

Это даёт:
- **Песочницу** — плагин не трогает ядро напрямую
- **Конвейер** — несколько плагинов могут обработать один вход последовательно (каждый дёргает ручки, ядро собирает результаты)
- **Бесконечную вложенность** — плагин может загрузить подплагин, тот получит свою копию реестра

### Отличия RON от Rhai

Конкретная ручка может быть доступна и там, и там.
Разница не в наборе ручек, а в природе вызова:

- **RON** — ручка вызывается один раз при загрузке конфига, с жёстко заданным значением
- **Rhai** — ручка вызывается многократно, по событиям, с вычисляемыми значениями
- **Плагин** — ручка вызывается из изолированной среды, результат проверяется ядром

### Общий лог (stderr-like канал)

**Проблема:** ручка ничего не возвращает. Плагин дёрнул `set_theme("dark")` и не знает, что произошло. Более того, если плагину нужно среагировать на изменение (например, другой плагин поменял цвета), у него нет механизма узнать об этом. Подписки на события — сложно, read-only ручки — ломают концепцию.

**Решение:** append-only лог, куда все пишут, и любой может прочитать.

```
ЯДРО:
  |  DEBUG | set_theme("dark") → OK
  |  DEBUG | set_tab_width(4) → OK
  |  DEBUG | PLUGIN_X: set_cursor_color("#fff")
  |  WARN  | PLUGIN_Y: remove_file("/etc/passwd") → REJECTED (sandbox)
  |  ERROR | PLUGIN_Z: insert_text() → "unexpected argument: color"

ПЛАГИН: читает последние N записей:
  "ага, тема поменялась на dark, поправлю свои цвета"
  "о, плагин X поменял курсор — сделаю так же"
```

**Как это работает:**

- Каждый вызов любой ручки — запись в лог: кто вызвал, с какими аргументами, что вернуло (OK / REJECTED / ERROR).
- Плагин может читать лог на любом этапе. Не подписка, а pull — сам решил, когда глянуть.
- Ядро тоже пишет в лог — видно всю картину.
- Лог хранит последние N записей (кольцевой буфер) — старые вытесняются.
- Никто ничего не синхронизирует. Append-only, каждый пишет своё, никто не удаляет чужое.

**Почему это лучше событий/подписок:**

- Никакого рантайма на уведомления — лог просто лежит, кто хочет — читает
- Отладка из коробки — видно кто что вызывал, в каком порядке, что пошло не так
- Один плагин может базироваться на другом: увидел в логе что PLUGIN_X вызвал set_font_size(16) — подстроился
- Ядро может анализировать лог на аномалии: "плагин дёргает одну ручку 1000 раз в секунду" → throttle/бан
- Если надо воспроизвести состояние — можно прогнать лог с начала (event sourcing)
